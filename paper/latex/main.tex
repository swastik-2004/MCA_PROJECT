\begin{abstract}
Players often complain that a particular game level is too hard, confusing or unfair, but turning
those complaints into a better level is slow, manual work that needs many rounds of play-testing.
We present LevelForge, a framework that takes a problem level and its player reviews, places the
level in a sandboxed \emph{digital twin}, and lets a team of AI agents redesign it. A large language
model (LLM) mines the reviews into a taxonomy of design problems and derives measurable design
targets. Nine agents, each running as its own service and communicating over the Agent2Agent (A2A)
protocol, then work as a master--worker team: a Director agent routes each diagnosed problem to the
specialist that owns it (difficulty, layout or rewards), a QA agent validates their plans, and a
Playtest agent evaluates every candidate. The agents use the twin through a Model Context Protocol
(MCP) tool server, and every candidate is play-tested by hundreds of simulated players on an
explicit master--worker cluster that schedules work dynamically and recovers from worker crashes
with bit-identical results. The developer receives the optimised level, the reason behind each
accepted change, and per-player-type statistics. On 24 starting levels with an identical simulation
budget, the agents raised mean quality from 0.536 to 0.773 (+44\%), beat random search on 16 of 24
levels and reached its final quality with about a third less budget; splitting the work across the
nine-agent team preserved quality exactly (0.772, 12 wins, 12 losses). Parallel play-testing reached a
$3.71\times$ speedup on 5 workers and $6.47\times$ on 12 logical cores, with an experimentally
determined serial fraction of 0.086.
\end{abstract}

\section{Introduction}
% =====================================================================
Game developers receive a constant stream of player feedback. On Steam alone, reviews are numerous,
and negative reviews in particular contain specific, actionable complaints~\cite{lin2019steam}:
``the second floor is way too hard'', ``I kept getting lost'', ``traps on the only path are unfair''.
Fixing a level in response is still largely manual. A designer has to interpret the complaints,
guess which change would address them, edit the level, and play-test it again, often many times,
because a change that fixes one complaint can cause another.

This paper asks whether that loop can be automated. Our approach follows the workflow a designer
would use, but replaces each manual step with an AI component:
\begin{enumerate}
\item \textbf{Listen:} an LLM reads the player reviews of a problem level and turns them into
measurable design targets (\emph{Generative AI}).
\item \textbf{Sandbox:} the level is loaded into a digital twin~\cite{grieves2017twin} of the
game, a fast, simplified simulation that keeps the level layout and game values.
\item \textbf{Redesign:} a team of agents diagnoses the level's weaknesses; specialist agents
propose alternative edits, and a Director agent decides (\emph{agentic AI}).
\item \textbf{Play-test:} hundreds of player agents play every candidate level simultaneously on
all CPU cores of a master--worker cluster (\emph{multicore architecture}).
\item \textbf{Report:} the developer receives the optimised level together with an explanation
of what changed and why, so the fix can be reviewed and learned from rather than applied blindly.
\end{enumerate}

LLMs can already generate game levels~\cite{todd2023level,sudhakaran2023mariogpt}, but generation
alone does not guarantee that a level is playable, balanced or aligned with what players asked for.
Judging that needs many playthroughs, which is computationally expensive. LevelForge therefore
combines LLM reasoning with large-scale parallel simulation, and keeps the LLM in a reasoning role
while a deterministic validator guarantees that every level stays playable.

The system is built from current agent standards: each agent is an independent A2A
service~\cite{a2aspec} that other agents discover through its published Agent Card, and the digital
twin is exposed as tools through MCP~\cite{mcpspec}, so the same tools serve our agents and any
external MCP-capable assistant.

\textbf{Contributions.}
(i)~A review-to-brief pipeline that converts free-text player feedback into quantitative design
targets and objective weights.
(ii)~A nine-agent team in a master--worker organisation over A2A: a Director that routes problems
to specialist agents with restricted action spaces, QA validation, a shared memory of failed plans,
and LLM or rule-based reasoning in every agent.
(iii)~An MCP tool server that makes the digital twin usable by any agent or assistant.
(iv)~A fault-tolerant master--worker simulation cluster with dynamic scheduling, plus a scaling,
granularity and fault-injection study.
(v)~A controlled comparison of random search, a single-agent loop and the agent team under the same
budget, and a developer-facing output: report, designer notes and a playable 3D game.

\section{Related Work}
% =====================================================================
\textbf{Procedural content generation (PCG).} Search-based PCG optimises content against an
evaluation function, often with evolutionary search~\cite{togelius2011sbpcg,shaker2016pcg}.
Experience-driven PCG models the player's experience and generates content to shape
it~\cite{yannakakis2011edpcg}. We follow the search-based framing, but derive the evaluation
function from player reviews, and use an agent loop with diagnosis instead of blind variation.

\textbf{Machine learning and LLMs for levels.} PCG via machine learning learns content from
existing examples~\cite{summerville2018pcgml}. Fine-tuned language models generate Sokoban
levels~\cite{todd2023level} and Super Mario levels from text prompts~\cite{sudhakaran2023mariogpt}.
These works focus on generating new levels; we focus on \emph{repairing} an existing problem level
in response to feedback, with simulation in the loop.

\textbf{Automated play-testing.} Procedural personas use agents with different objectives to
represent different play styles~\cite{holmgard2019personas}. Our player agents follow this idea
with three cost-based planning personas, and use the gap between them as a measure of skill
expression.

\textbf{LLM agents and annotation.} ReAct interleaves reasoning and actions~\cite{yao2023react}, and
Reflexion keeps a verbal memory of failed attempts~\cite{shinn2023reflexion}; our critic's memory of
failed fixes is a lightweight form of the latter. LLMs have been shown to match or outperform crowd
workers on text annotation~\cite{gilardi2023annotation}, which motivates LLM-based review labelling.

\textbf{Multi-agent LLM systems and protocols.} AutoGen~\cite{wu2023autogen} composes LLM agents
that converse to solve tasks, and MetaGPT~\cite{hong2024metagpt} assigns them software-engineering
roles with standard procedures. These frameworks run agents inside one program. We instead follow
two open protocols: A2A~\cite{a2aspec} for agent-to-agent tasks between separate services, and
MCP~\cite{mcpspec} for agent-to-tool access.

\textbf{Parallel performance.} Our cluster follows the master--worker pattern~\cite{mattson2004patterns};
we analyse scaling with Amdahl's law~\cite{amdahl1967} and the Karp--Flatt experimentally
determined serial fraction~\cite{karpflatt1990}.

\section{Method}
% =====================================================================
\subsection{Review Mining and the Design Brief (GenAI)}
Reviews are sent to the LLM in batches, which labels each review with zero or more problems from a
fixed taxonomy: \emph{too hard}, \emph{too easy}, \emph{repetitive}, \emph{confusing layout},
\emph{unfair traps} and \emph{little reward for exploring}, plus praised aspects. Batches are sent
concurrently with a thread pool, because the calls are I/O-bound; a keyword classifier is the
offline fallback. Let $s_x$ be the share of reviews that mention problem $x$, and
$d=s_\text{hard}-s_\text{easy}$. The brief sets a target completion rate and a target share of
health lost by players who finish:
\begin{align}
c^* &= \operatorname{clip}(0.65 + 0.35\,d,\; 0.45,\; 0.85),\\
h^* &= \operatorname{clip}(0.40 - 0.30\,d,\; 0.20,\; 0.60),
\end{align}
and raises the weight of the quality component each complaint relates to: engagement by
$0.4\,(s_\text{repetitive}+s_\text{empty})$, flow by $0.4\,s_\text{confusing}$ and skill by
$0.4\,s_\text{unfair}$. Table~\ref{tab:brief} shows the result for the 48 sample reviews used in
this paper: \emph{too hard} was the most common complaint (23\%), so the brief asks for a level that
more players finish ($c^*=0.71$ instead of the default 0.65) and that costs them less health
($h^*=0.35$ instead of 0.40). Each complaint is also mapped to a likely cause and a candidate
design change (e.g.\ \emph{unfair traps} $\to$ traps on forced routes $\to$ move traps to optional
routes); these are included in the generator's LLM prompt and in the report.

\subsection{Digital Twin}
A level is a character grid of walls, floor, start, exit, key, locked door, monsters, traps,
health potions and coins. A turn-based simulator implements the rules: monsters have 3 health and
hit with probability 0.6; a monster may strike a player walking past it (probability 0.25); traps
trigger with probability 0.6 for 3 damage; potions heal 4; players start with 10 health (maximum 12).
A validator checks that a level is well-formed and that the exit is reachable (a door needs a key
reachable before it).

The twin mirrors a real-time game, \emph{LevelForge: Breach}: a first-person 3D shooter built with
Three.js that runs in the browser. Its levels are built from the same grids and use the same values
(monsters become hunter drones, traps become proximity mines, potions become med-kits, coins become
data cores). Real-time aiming, dodging and enemy movement are abstracted into discrete encounters
so that thousands of playthroughs take seconds. All quality numbers in this paper are measured on
the twin. Fig.~\ref{fig:game} shows the game.

\subsection{Player Agents}
Each player agent plans with Dijkstra search over a persona-specific cost model, re-planning as the
level changes (picked-up items, defeated monsters). The \emph{rusher} pays almost nothing for danger,
the \emph{cautious} agent pays heavily for traps and monsters and detours to heal, and the
\emph{explorer} collects coins before exiting. Randomness in fights and traps comes from a seeded
generator, so each playthrough is defined by the tuple (level, persona, seed).

\subsection{Metrics and Quality Score}
For each level we aggregate completion, death and timeout rates, damage, backtracking ratio $\beta$
(steps that revisit tiles), exploration $x$, coin collection $\kappa$ by explorers, health lost by
finishers $h$, and completion per persona $c_p$. Five components in $[0,1]$ are
\begin{align*}
q_\text{bal} &= 1-\tfrac{|c-c^*|}{\max(c^*,1-c^*)}, &
q_\text{eng} &= 0.6\,\kappa + 0.4\min(1, x/0.6),\\
q_\text{flow} &= 1-2\beta, &
q_\text{skill} &= \tfrac{c_\text{cautious}-c_\text{rusher}}{0.35},\\
q_\text{ten} &= 1-\tfrac{|h-h^*|}{\max(h^*,1-h^*)}, &&
\end{align*}
each clipped to $[0,1]$, and the quality score is the weighted mean
$Q=\sum_k w_k q_k / \sum_k w_k$ with brief-derived weights. Balance penalises both under- and
overshooting the target; skill expression rewards levels where careful play beats reckless play.

\subsection{The Agent Team (A2A)}
Each agent runs as its own HTTP service built with the official A2A SDK (protocol v1.0). It
publishes an Agent Card (name, description, skills, endpoint) at a well-known URL; the Director
discovers all eight workers from their cards at start-up and then sends them tasks as JSON-RPC
\texttt{SendMessage} requests. A task carries one JSON object naming the skill to run; the worker
returns its result as a task artifact, or a failed task with the error. Algorithm~\ref{alg:team}
shows one optimisation run.

\textbf{Routing.} The Playtest Analyst diagnoses the current best level with a fixed vocabulary of
problems (e.g.\ \emph{too\_hard}, \emph{low\_skill\_expression}). The Director routes each of the top
three problems to the specialist that \emph{owns} it: difficulty problems (too hard/easy, damage) to
the Difficulty Specialist, flow and skill-expression problems to the Layout Specialist, engagement to
the Reward Specialist. The top problem gets $k-2$ plan slots and the next two one slot each; with only
two problems the Director merges one plan from each owner into an extra candidate, and spare slots go
to exploration. Specialists only see their own edit operations (e.g.\ the Reward Specialist cannot
add monsters), which keeps their prompts short and their plans on-topic. They are called in parallel.

\textbf{Validation, decision and memory.} The QA Validator applies each plan through MCP and rejects
plans that change nothing or duplicate another candidate. The Playtest Analyst evaluates all
remaining candidates in one job; the Director accepts the best if it beats the current level and
otherwise rolls back. Two memories steer later rounds: diagnosed priorities whose fixes failed are
demoted, and edit plans already tried on the current level are shared with all specialists so they
are not repeated.

\textbf{Reasoning.} Every agent has an LLM mode and a rule mode. With an API key, the Review Analyst,
Level Architect, Playtest Analyst (diagnosis), specialists and Reporter call the LLM; any failed call
falls back to rules for that step. The LLM never edits the grid directly: it chooses structured edits
(add or remove a monster, trap, potion or coin on or off the main route; open a loop; add or remove a
lock), which are validated and applied deterministically, so every level stays playable. A
single-agent version of the same loop, a LangGraph~\cite{langgraph} state graph with one critic and
one optimiser, serves as the baseline in Section~\ref{sec:results}.

\begin{algorithm}[t]
\caption{Director: one optimisation run (all calls are A2A tasks)}
\label{alg:team}
\small
\begin{algorithmic}[1]
\Require reviews, level $L_0$ (optional), rounds $R$, plans $k$, runs $n$
\State $B \gets$ ReviewAnalyst.\Call{build\_brief}{reviews}
\State $L^\star \gets$ LevelArchitect.\Call{initial\_level}{$L_0$, $B$}
\State $Q^\star \gets$ PlaytestAnalyst.\Call{playtest}{$\{L^\star\}$} \Comment{MCP $\to$ cluster}
\For{$r = 1$ to $R$}
  \State $D \gets$ PlaytestAnalyst.\Call{diagnose}{$L^\star$, failed priorities}
  \State $A \gets$ \Call{Route}{$D$, $k$} \Comment{problem $\to$ owning specialist}
  \State $P \gets \bigcup_s$ Specialist$_s$.\Call{propose}{$A_s$, tried plans} \Comment{parallel}
  \State $C \gets$ QAValidator.\Call{validate\_plans}{$L^\star$, $P$} \Comment{MCP apply\_edits}
  \State scores $\gets$ PlaytestAnalyst.\Call{playtest}{$C$} \Comment{one job, $|C|\cdot 3n$ runs}
  \If{$\max Q(C) > Q^\star$} accept best, clear tried plans
  \Else{} roll back, mark $D$.priority as failed \EndIf
\EndFor
\State \Return $L^\star$, Reporter.\Call{write\_notes}{history}
\end{algorithmic}
\end{algorithm}

\subsection{Tool Layer (MCP)}
The digital twin is exposed by an MCP server built with the official MCP SDK. Its ten tools
(Fig.~\ref{fig:arch}) cover validation, procedural generation, repair, structured edits, level
summaries, play-testing and cluster control. \texttt{evaluate\_levels} takes several grids and
plays them all in one cluster job with the same random seeds (common random
numbers~\cite{law2015simulation}), so score differences come from the levels, not from luck. The
agents reach the server over Streamable HTTP; the same server also runs over stdio, so an MCP-capable
assistant (e.g.\ a desktop chat client) can evaluate and edit levels with exactly the tools our
agents use.

\subsection{Master--Worker Simulation Cluster}
Every playthrough (level, persona, seed) is independent, so play-testing is embarrassingly parallel.
The cluster makes the master--worker pattern~\cite{mattson2004patterns} explicit. The master splits a
job into chunks of 8 playthroughs and keeps them in a ready queue. Each worker process has its own
pipe and holds at most two chunks; whenever it returns one, the master sends the next. Fast workers
therefore simply take more chunks (dynamic self-scheduling), which balances the uneven cost of
playthroughs (Section~\ref{sec:scaling}). The master waits on the workers' pipes and on their process
sentinels together. If a worker dies, its unfinished chunks are put back at the front of the queue
and a replacement process is started; because every task is seeded, the job's result is identical
to a run without the crash. Processes are used instead of threads because the simulator is
CPU-bound Python and the global interpreter lock would serialise threads (review labelling, which
waits on the network, uses threads). Workers are started once per run.

\subsection{What the Developer Receives}
The goal is a level the developer can \emph{learn from}, not just a new grid. Each run produces an
HTML report with the review analysis, the score per round, every candidate the agents tried with its
score, the accepted plan per round, before/after levels, animated replays of each player agent, and
designer notes (Table~\ref{tab:case} is an excerpt). Finally, the levels are exported into the
playable 3D game, so the team can experience the problem level and its optimised version directly.
For the case study of Section~\ref{sec:case}, the notes read:

\begin{quote}
\small\itshape
``The initial level scored 0.48; after optimisation it scores 0.89. Completion moved from 32\% to
72\% against a review-derived target of 71\%. Backtracking went from 12\% to 4\% of steps, and
explorers now collect 100\% of the coins (was 77\%). Per-player-type completion (rusher / cautious /
explorer): 31\%/31\%/34\% $\to$ 66\%/100\%/51\%.''
\end{quote}

\noindent These notes come from the rule-based finalizer, which fills a template; the LLM
finalizer writes free-form notes that also explain \emph{why} each change helped.

\subsection{Implementation}
LevelForge is written in Python (about 5,000 lines). Agents use the official A2A SDK on Starlette
and Uvicorn; the tool server uses the official MCP SDK; the cluster uses the standard
\texttt{multiprocessing} library. The LLM client uses only the standard library and talks to an
OpenAI-compatible endpoint (Groq) in JSON mode, with retries that honour \texttt{Retry-After}. One
command (\texttt{run\_team.py}) starts the MCP server with its workers and the nine agent services
on the local machine, sends the job to the Director and writes the report; a second script crashes
a chosen worker during a run to demonstrate recovery. All randomness is seeded, so runs are
reproducible. The game is a single offline HTML file (Three.js) generated from the runs' data.

\textbf{Hardware.} A laptop with \fillme{CPU model}, \fillme{N} physical cores and 12 logical
cores, \fillme{RAM} GB RAM, Windows, Python \fillme{version}. The GPU was not used for the
experiments.

\textbf{LLM.} GPT-OSS-120B~\cite{openai2025gptoss} served through the Groq API, with JSON output
mode and low reasoning effort. Every LLM step falls back to rules if a call fails.

\textbf{Optimisation study.} Since real reviewed levels were not available, 24 procedurally
generated levels serve as stand-ins for problem levels (mean completion 58\%, well below the 71\%
target). All methods start from the same level and get the same budget: 6 rounds $\times$ 4
candidates $\times$ 300 playthroughs. Methods: no optimisation (raw); random search (same loop,
random edits, no diagnosis); the single-agent loop; and the nine-agent A2A team (both with rule-based
reasoning, so that results are reproducible and free of API limits).

\textbf{LLM study.} An earlier run on 4 levels compared LLM and rule-based reasoning in the
single-agent loop (99 API calls, 425\,s). It is small because of free-tier API rate limits.

\textbf{Statistics.} Paired comparisons per level: exact two-sided Wilcoxon signed-rank
test~\cite{wilcoxon1945} and sign test.

\textbf{Scaling study.} 3,600 playthroughs (6 levels $\times$ 3 personas $\times$ 200) at 1--12
workers, best of 3 repeats: first with the standard process pool (chunk size $n/(4p)$, then chunk
sizes 1, 8, 180 and 720 at 5 workers), then with the master--worker cluster, including runs in which
1 or 2 workers are killed mid-job.

\subsection{Optimisation Quality}
Table~\ref{tab:main} summarises the 24-level study. All three optimisers improved every level over
the raw level (Wilcoxon $p<0.001$ each): $+40\%$ for random search and $+44\%$ for both agent
systems. The single-agent loop beat random search on 16 of 24 levels (mean paired gain $+0.021$,
Wilcoxon $p=0.072$, sign test $p=0.152$), and landed closer to the completion target (74\% vs.\
80\%). The advantage over random search is consistent in direction but, at this sample size, not
significant at the 5\% level; in an earlier 12-level run it was ($p=0.034$), which shows how much the
result depends on which levels are drawn. Fig.~\ref{fig:conv} shows the clearer benefit:
efficiency. Both agent systems reach random search's final quality (0.752) after 4--5 of the 6
rounds, i.e.\ with about a third less simulation budget.

\subsection{Single Agent vs.\ Agent Team}
Splitting the work across nine A2A agents did not change quality: the team scored $0.772$ against
$0.773$ for the single-agent loop, winning 12 levels and losing 12 (Wilcoxon $p=0.886$). Per-level
differences were large in both directions (from $-0.11$ to $+0.16$), because a different sequence of
plans leads to a different local optimum. A team run exchanged 34.5 A2A messages per level on average.
Reaching parity required two design decisions. Our first team version, which gave every specialist
a fixed share of the plan slots regardless of the diagnosis, scored $0.735$ on the first 12 levels
(11 losses out of 12). Routing each diagnosed problem to its owner, and sharing the memory of tried
plans across specialists, closed the gap. The benefit of the team is therefore not higher quality
but a modular system: each agent is a separate service with a narrow role, can be replaced or
scaled independently, and can switch between LLM and rule reasoning without affecting the others.

\subsection{LLM vs.\ Rule-Based Reasoning}
In the earlier 4-level study of the single-agent loop (Table~\ref{tab:llm}) the LLM agent won 2 of 4 levels against random search
and 2 of 4 against the rule-based agent. With 4 levels no difference is statistically detectable
(the smallest possible two-sided sign test $p$-value is 0.125), so we report the methods as
comparable. The LLM agent had the highest variance: the best result on two levels (0.804, 0.844)
and the worst agent result on another (0.655).

\subsection{Case Study: Repairing a Problem Level}
\label{sec:case}
Fig.~\ref{fig:levels} shows a problem level before and after optimisation by the single-agent loop, and Table~\ref{tab:case}
shows what the developer sees round by round. Only 32\% of playthroughs reached the exit (target
71\%) and, worse for design, reckless and careful players did equally badly (31\% vs.\ 31\%), so
skill was not rewarded. After six rounds and 11,250 simulated playthroughs (19\,s),
quality rose from 0.477 to 0.895: completion 72\%, backtracking down from 12\% to 4\% of steps, and
per-persona completion (rusher/cautious/explorer) changed from 31/31/34\% to 66/100/51\%, so careful
play now pays off. Only 12 tiles changed, which makes the fix easy for a designer to review. The
component scores moved as follows: balance 0.45$\to$0.98, engagement 0.62$\to$0.86, flow
0.77$\to$0.92, skill 0.02$\to$0.97 and tension 0.42$\to$0.63; tension improved least, because
finishers still lose 59\% of their health against a target of 35\%. Fig.~\ref{fig:persona}
shows the per-persona effect, which is the part of the result a designer is most likely to act on.
The agent team, run on the same level with the same budget (and one injected worker crash),
reached 0.744 with completion exactly on target (71\%); four of its five accepted plans came from the
Difficulty Specialist. As Table~\ref{tab:main} shows, such per-level differences average out.

Two further runs show the LLM in its generative role. In the full LLM pipeline, the LLM designed a
corridor-based level from the brief alone (quality 0.604, 100\% completion, i.e.\ too easy); the
LLM agents then raised it to 0.879 with 79\% completion, mainly by placing hazards in corridors

objectives, even when the scoring rules are given in the prompt.

\subsection{Parallel Scaling}
\label{sec:scaling}
Table~\ref{tab:scaling} and Fig.~\ref{fig:speedup} report speedup $S_p=T_1/T_p$, efficiency
$S_p/p$ and the Karp--Flatt metric
$e=(1/S_p-1/p)/(1-1/p)$~\cite{karpflatt1990}. Throughput rose $6.5\times$ from 1 to 12 workers;
pool start-up cost 0.13--0.22\,s and is paid once per run. The serial fraction $e$ stayed roughly
constant (0.074--0.113, mean 0.086). A constant $e$ points to a fixed serial portion (task creation,
pickling levels, aggregating results) rather than overhead that grows with the number of workers.
Amdahl's law~\cite{amdahl1967} with $f=0.086$ bounds the speedup at about $11.6\times$. Efficiency
falls faster beyond \fillme{N physical cores} workers because extra workers share physical cores
through hyper-threading \fillme{and the CPU mixes performance and efficiency cores, if applicable}.

\textbf{Task granularity.} At 5 workers, throughput was 1,205 sims/s with chunk size 1, 1,168 with
8, 997 with 180 ($=n/4p$) and 909 with 720 ($=n/p$). Contrary to the common advice to batch small
tasks, the smallest chunks were fastest ($+21\%$ over $n/4p$). A playthrough costs about 3.7\,ms,
much more than dispatching it, but its cost varies between levels and personas, so large chunks
leave some workers idle at the end of a sweep (load imbalance). We therefore changed the default to
small chunks (at most 8). The scaling table above used the earlier $n/4p$ setting, so it is a
conservative estimate.

\subsection{Master--Worker Cluster and Fault Tolerance}
The explicit master--worker cluster matched the throughput of the standard process pool
(\fillme{cluster: sims/s and speedup at 5 and 12 workers, from \texttt{benchmark\_cluster.py}}),
so making scheduling and failure handling explicit cost no performance. Killing workers mid-job did not change any result:
with 1 and 2 crashes per job the aggregated metrics were bit-for-bit identical to the crash-free run,
at a cost of \fillme{extra seconds for 1 and 2 crashes} (re-running the lost chunks and starting a
replacement process). In the agent-team case study, one crash was injected in round 2: the master
re-queued 16 playthroughs, started worker W6, and the round completed normally.

\textbf{Protocol overhead.} In a team run the A2A and MCP layers add little to the simulations:
\fillme{protocol overhead per play-test call (ms) and median other A2A message (ms), from
\texttt{benchmark\_cluster.py}}, against about 2--3\,s of simulation per round. Messages that do not
trigger simulations (diagnosis, proposals, notes) are dominated by LLM latency when an API key is
used, and the three specialists' LLM calls run in parallel.

\section{Discussion and Limitations}
% =====================================================================
The agents' main benefit over random search is efficiency: equal quality with about a third
fewer simulations, and a modest gain at equal budget that is consistent in direction but not
statistically significant on 24 levels. Turning the single loop into nine A2A agents kept quality
unchanged and bought modularity, standard interfaces (A2A, MCP) and fault tolerance; it is an
engineering gain, not an accuracy gain. Its accepted changes are also
interpretable (Table~\ref{tab:case}), which matters when the goal is a fix that a developer
understands. LLM reasoning was comparable to hand-written rules but less consistent; its
advantages are designing levels from scratch, natural-language explanations, and needing no
hand-written playbook, while its costs are API latency and rate limits (425\,s for 4 levels vs.\
seconds offline).

\textbf{Why structured edits?} LLM-written grids can violate hard constraints (uneven rows,
unreachable exits), which is why the generator needs self-correction and deterministic repair. Restricting the LLM to choosing among validated edit operations keeps its
reasoning role (what to change, where, and why) while guaranteeing playability, and makes every
change small enough for a designer to review.

\textbf{Generality.} The framework needs three things from a game: a level representation that
edits can be applied to, a fast simulator with a few player personas, and a complaint taxonomy
mapped to metrics. The agent loop, the parallel engine and the statistics are game-independent, so
the same approach could apply to, for example, platformer or puzzle levels.

\textbf{Threats to validity.} The player agents are rule-based and only approximate human players;
the quality score is a designed proxy and we do not claim it measures fun. The 48 reviews are
synthetic and the problem levels in the main study are procedurally generated stand-ins, so claims
about real players require real reviewed levels. The twin abstracts real-time shooting into
discrete encounters. LLM labelling varies slightly between runs, so each experiment computes the
brief once and shares it across methods. The LLM study used only 4 levels, and the team was
evaluated with rule-based reasoning; its LLM mode was used in demonstrations but not benchmarked.
All agents ran on one machine; A2A and MCP would allow spreading them over several.

% =====================================================================
\section{Conclusion and Future Work}
% =====================================================================
LevelForge takes a level that players complain about, turns their reviews into measurable targets,
and improves the level with a team of nine agents that communicate over A2A, use the digital twin
through MCP, and play-test on a fault-tolerant master--worker cluster, returning an optimised level
with an explanation the developer can learn from. The agents reached random search's final quality
with about a third less budget, and decomposing the work into agents preserved quality while making
each part replaceable. Future work: real reviews paired with real levels, a larger LLM study of the
team, running agents and workers on several machines, learned player models, modelling shooting
directly in the twin, multi-objective optimisation for competing targets, and a user study with
human players.
